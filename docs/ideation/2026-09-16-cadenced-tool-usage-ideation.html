1 · S1 · Acquisition routes

A connection and cadence for each tool

Give each tool one clear connection choice showing what it can supply, required authority, personal or organization scope, and the freshness target that route can support. Reuse existing scheduled collectors where available; explicitly offer export or owner-assisted renewal where a personal read API has not been verified. Public product terms and personal usage remain separate rows.

What this adds
A consistent connection choice and cadence/freshness contract across providers; GitHub/Devin daily collection already exists.
Basis
direct: The existing subscription includes refreshCadence: "DAILY", metricKey and attributionScope. The private Wispr panel separately instructs the owner to retain and transcribe selected evidence.
Rationale
This directly answers the connection question: select an evidence route that the provider and the owner actually permit, then attach a useful cadence. It extends the existing collectors rather than inventing a universal usage API.
Downsides
Provider research and account-tier checks remain tool-specific. A generic route catalog can become premature infrastructure if built before a small set of real connectors.

2 · S2 · Acquisition routes

Guided Wispr renewals

Offer a weekly or monthly private renewal for snapshot-backed metrics, with vendor instructions and the last reviewed measurement beside the new capture. Preserve the supplied image and assistant-extraction provenance separately, require owner review of extracted claims, and retain the old evidence when a renewal is missed. No personal API is assumed.

What this adds
Renewal prompts and review continuity. The present private text form exists; automated screenshot ingestion does not.
Basis
direct: The intake validator states: “Selected copied text and manual transcriptions must be USER_SUPPLIED.” User-supplied images and assistant-extracted text therefore need distinct provenance; a renewal cannot erase that distinction.
Rationale
A repeated personal Wispr snapshot can be useful without pretending it is an API sync. A guided renewal makes the manual part short and reviewable.
Downsides
Someone still supplies the evidence. Supporting assistant-extracted image text requires an explicit provenance and owner-review design; merely relabeling it USER_SUPPLIED would be wrong.

3 · S3 · Suite changes and consent

A weekly suite review

Accumulate changes suggested by already authorized sources into one private review: a new tool candidate, a reconnect need, a changed identity, or an explicit owner archive proposal. Keep the current approved suite stable while approved exact-metric usage continues refreshing; stale data alone never removes a tool.

What this adds
A consolidated, evidence-backed suite-change review. Private draft imports and owner publication controls already exist.
Basis
direct: “Authorized automation can populate `RawEvidence` and propose `DraftProp`s. The user controls review and publication; automation can never merge to `main`.” That supports private suite suggestions, not a claim that recurring discovery is implemented.
Rationale
The suite evolves more slowly than usage counters. One periodic review can keep the owner in control while routine approved values refresh quietly.
Downsides
Discovery coverage is limited to authorized sources. An app name or an absence of activity does not establish paid adoption or justify removal.

4 · L2 · Acquisition routes

Preserve what each metric means

Give every metric a reusable semantic identity covering unit, transformation, aggregation level, comparison population, and provider definition version. Connectors, owner-assisted snapshots, history, and UI labels all point to the same definition, while changed meanings append a new version rather than rewriting prior observations.

What this adds
Versioned metric meaning shared between capture, history and display; existing scope and unit fields are a foundation.
Basis
external: Wispr describes the desktop breakdown as “A bar chart of your dictation time”. Its display counts are transformed for some categories; its speed percentile compares against keyboard typing speeds. A recent number alone is not a complete metric.
Rationale
The Wispr documentation demonstrates why equally recent numbers can mean different things. Retaining definitions prevents an integration from making precise but invalid comparisons.
Downsides
Definition maintenance adds ongoing work. Start with observed ambiguities and a few fields, rather than a universal metric ontology.

5 · P1 · Freshness and recovery

Show how current the evidence is

Show retrieval attempt, last successful capture, and evidence measurement window as separate timestamps on every usage card. Preserve the last good value and label it stale when collection fails, so a fresh cron run is never confused with fresh underlying evidence.

What this adds
One understandable evidence-freshness display across routes; attempt/success fields and stale handling already exist.
Basis
direct: The schema stores lastSuccessfulAt, lastAttemptedAt and lastError. Existing refresh retains activity with freshness: "STALE" after failure. These fields support a clearer cross-route display; that display is the proposed addition.
Rationale
Show separately when collection succeeded, what period the metric covers, and when another check is expected. This makes the cadence trustworthy without promising live data.
Downsides
A three-date display can become clutter. Unknown measurement periods and source lag need clear wording, not a single green check.

6 · I1 · Freshness and recovery

Ask for attention only when needed

Invert the review workload: approved exact-scope refreshes stay silent when the semantic value and metric contract are unchanged. Open an inbox item only for failure, staleness, source-shape change, scope drift, or a meaningful usage change outside an owner-set tolerance.

What this adds
Deduplicated actionable health notices. Existing run classification and last-good preservation should be reused.
Basis
direct: Official-page refresh distinguishes INCOMPLETE, BASELINE, REPARSED, UNCHANGED and CHANGED. Classification already exists; an actionable, deduplicated notice is the proposed addition.
Rationale
Daily collection should not demand daily attention. A private health queue can focus on failed access, overdue evidence, scope changes and source-definition changes.
Downsides
Over-sensitive thresholds create noise. Ordinary count growth should remain a routine update when its exact scope and meaning are already approved.

Codebase Context

The local source checkpoint is 4d2171badc0cd9ea310a2c5a615a9313085ccde4. It includes GitHub and Devin connector actions, daily approved-metric refresh, and a separate daily public-source path for Wispr. The 15-minute public-source poll is a scheduler frequency; it is not a claim that every source refreshes every 15 minutes.

“Connected activity is private until I approve this card.”

Connector snapshot wording · line322. Existing approved exact-metric subscriptions can subsequently update public activity. That permission is distinct from publishing a new import, broadening a metric, or reading an additional source.

Official Wispr documentation offers personal share-card images and an Enterprise-admin CSV route. No documented personal native-app usage read API was found in the bounded search; that is not proof none exists. The developer transcription API is a different surface. No account-tier or credential readiness was verified for the owner.

Devin's current local collector uses organization metrics. Its documented per-user daily consumption endpoint is Enterprise-only and needs a service user with the appropriate consumption permission; it must not be presented as an ordinary personal connector capability.

Source definitions matter: Wispr's breakdown uses dictation-time shares and transformed display counts. Its WPM percentile uses a keyboard-typing comparison population. The private screenshot values remain outside this repository artifact.

The current GitHub collector uses GraphQL contributions. GitHub Events documentation was consulted as an adjacent polling example; its latency and retention limits do not characterize the implemented collector.
