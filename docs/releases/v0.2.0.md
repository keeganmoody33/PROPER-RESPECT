### One-time setup

Do this **before the first tag**. GitHub can't be made to enforce it from the
workflow, so the workflow checks it instead:

- **Both environments need you, the repository owner, as the only required
  reviewer.** The `verify` job reads each environment's protection rules and
  stops the release if either environment is missing or can't be read, or if
  its required reviewers aren't exactly your account. A team or any other
  reviewer fails the check.
- **Put each secret in its environment only** (Settings, Environments, the
  environment, Environment secrets). Delete any **repository or organization**
  secret named `CONVEX_DEPLOY_KEY` or `VERCEL_TOKEN`. A same-named broader
  secret would still reach the job, and each deploy job's first step only
  checks that its values aren't empty; it can't tell where they came from.
- **Limit both environments to `v*` tags** (the environment's deployment
  branches and tags), as K02 says.

1. **GitHub environment `production-backend`**, with you as a required
   reviewer:
   - environment secret `CONVEX_DEPLOY_KEY`: a **new** production deploy key for
     `striped-chicken-693`, created in the Convex dashboard (deployment
     settings, Deploy keys) with **both** `deployment:deploy` and
     `deployment:env:write`. The second lets the workflow record
     `DEPLOYED_SHA`. Without it, the "Record the deployed commit" step fails
     after the backend has already deployed. Don't copy the key that Vercel
     holds today; item 6 below removes it, and step 7 revokes it.
2. **GitHub environment `production-frontend`**, with you as a required
   reviewer:
   - environment secret `VERCEL_TOKEN`, scoped to the team that owns the
     project, with an expiry;
   - environment **variables** `VERCEL_ORG_ID` (`team_MfB5K2Npy5oy5SFJ2g9nbL5W`)
     and `VERCEL_PROJECT_ID` (`prj_yxsUnnPW0ka8mkFr7l66eUSzJgT8`). They
     identify the project and aren't secret. The workflow also pins these two
     values and stops if the variables differ, so a stale repository or org
     variable with the same name can't send the deploy to another project.
     Moving to another Vercel project means changing the workflow in a
     reviewed PR.
3. **Repository variable `PUBLIC_HANDLE`** = `lecturesfrom`, set at the
   repository level, not on an environment. The `verify` job stops the
   release before anything deploys if it's missing or isn't a valid handle,
   then passes that exact value to the smoke test. (`/keegan` redirects once
   the migration has run.)
4. **Repository variable `PUBLIC_CONVEX_URL`** = the production Convex URL
   (`https://striped-chicken-693.convex.cloud`, the value of
   `NEXT_PUBLIC_CONVEX_URL` in Vercel's production environment). The `verify`
   job takes the deployment name from it, and the `backend` job refuses any
   `CONVEX_DEPLOY_KEY` that isn't a production key for that deployment, so a
   dev key or another deployment's key can't deploy somewhere else. The
   receipt witness (R11) reads the same variable. The workflow also pins
   `striped-chicken-693` and stops if the variable names another deployment,
   so an org-level variable of the same name can't redirect it. Moving
   production to another deployment takes a reviewed change to the workflow.
5. Confirm `vercel.json` on the commit you tag builds with
   `npm run deploy:check && npm run build` (no `convex deploy`).
6. **Delete the old `CONVEX_DEPLOY_KEY` from Vercel, before tagging.** Remove
   it from **every** environment of the Vercel project (Production, Preview
   and Development). Vercel passes project variables to installs and builds,
   so leaving it there would expose a key that can change the production
   backend to the first frontend build. Nothing needs it any more: the build
   is frontend-only, and the preflight checks the key only when it's present.
   Removing a variable doesn't change running deployments, so production and
   Instant Rollback keep working. Step 7 revokes the key itself.
7. The `frontend` job runs the Vercel CLI version pinned in
   `release-tools/package.json` and its lockfile, installed without install
   scripts. To update the CLI, change both in a reviewed PR.

## Steps

### 1. Tag and push

```sh
git fetch origin
git checkout origin/main
git tag -a v0.2.0 -m "v0.2.0"
git push origin v0.2.0
```

The `verify` job refuses a tag whose commit is not on `main`, then runs the
tests, lint and typecheck.

### 2. Approve `backend`

Approve the `backend` job in the Actions run. It runs `npx convex deploy -y`,
then `npx convex env set DEPLOYED_SHA <commit>`. The job's deploy key scopes
both commands to production, so they carry no `--prod`. To set the value by
hand from your own logged-in checkout, add the flag:
`npx convex env set --prod DEPLOYED_SHA <commit>`.
The deploy is additive: new tables and fields, no destructive schema change.

### 3. Run the handle migration (skip if the premise check says it ran)

This moves the published `/keegan` snapshot to `/lecturesfrom` and leaves
`/keegan` as a redirect. It only works after step 2, because the function
arrived with #52.

The migration takes nine arguments (`convex/publicationMigration.ts`). Use the
retained values from "Release gate and operator sequence" in
`docs/verification/2026-09-22-canonical-owner-profile.md` (kept outside Git).
If they are lost, rebuild them:

| Argument | Where it comes from |
|---|---|
| `ownerId` | The owner's `users` row `_id` (Convex dashboard, production, Data, `users`, the row with handle `lecturesfrom`). |
| `expectedSubject` | That row's `authSubject`. |
| `publicationId` | The `publishedProfiles` row with handle `keegan`: its `_id`. |
| `expectedRevision` | That row's current `revision`. |
| `expectedSeedKey` | `keegan` (`convex/seed.ts`). |
| `fromHandle` | `keegan`. |
| `toHandle` | `lecturesfrom`. |
| `expectedProfileHash` | See below. |
| `dryRun` | `true` first, then `false`. |

To compute `expectedProfileHash`, copy that `publishedProfiles` row (or just
its `profile` value) from the dashboard into a local file outside Git, then
run:

```sh
node --experimental-strip-types scripts/migration-profile-hash.mjs /path/outside/git/keegan-row.json
```

It prints the lowercase hex SHA-256 of
`canonicalJson({ ...profile, handle: "keegan" })`, the same value the
migration checks. A test (`src/domain/migration-profile-hash.test.ts`) pins it
to the repo's own `canonicalJson` and `sha256`.

Dry run, then apply:

```sh
npx convex run --prod publicationMigration:moveSeededPublication '{"ownerId":"<ownerId>","expectedSubject":"<authSubject>","publicationId":"<publicationId>","expectedRevision":<revision>,"expectedSeedKey":"keegan","fromHandle":"keegan","toHandle":"lecturesfrom","expectedProfileHash":"<hash>","dryRun":true}'
```

Expect `"status": "ready"` with the right `cardCount`. Then run the same
command with `"dryRun":false` and expect `"status": "migrated"`. A repeat
returns `"already-migrated"` and changes nothing. Keep the command outputs as
the release receipt, outside Git if they include identifiers.

### 4. Approve `frontend`

Approve the `frontend` job. It deploys to Vercel production with the commit and
tag as deployment metadata, then fails unless:

- `proper-respect.com` is an alias of the new deployment, and
- `/`, `/lecturesfrom` and `/sitemap.xml` return 200.

### 5. Verify

```sh
curl -s -o /dev/null -w '%{http_code}\n' https://proper-respect.com/lecturesfrom   # 200
curl -s -o /dev/null -w '%{http_code} %{redirect_url}\n' https://proper-respect.com/keegan   # 308 to /lecturesfrom
```

Then sign in as the owner and confirm the collection still shows the four
published cards at `lecturesfrom`.

### 6. If the frontend fails

Roll back with Vercel **Instant Rollback** in the dashboard. On the Hobby plan
it can only go back to the previous production deployment. Keep the additive
backend. **Never reseed, and never run a destructive backend rollback.**

After an Instant Rollback, Vercel stops giving the production domain to new
deployments until one is promoted. The next release must start with
`vercel promote` (see [TEMPLATE.md](TEMPLATE.md)).

### 7. Revoke the old deploy key

Once step 2 has deployed with the new key from `production-backend`, nothing
uses the key Vercel held, which setup item 6 already removed from Vercel.
Removing a variable doesn't stop a key working, so **revoke** it in the Convex
dashboard (production deployment settings, Deploy keys). Revoke only that old
key, not the new one in `production-backend`.
