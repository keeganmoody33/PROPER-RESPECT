# ADR-031: The API — Public and Internal

> Parked: not active MVP scope. Revisit only after the core product-stack profile works.


## Status
Accepted — 2026-06-05

## Context
The API serves both internal frontend needs and external third-party integrations. How do we structure it? What are the rate limits?

## Decision

### The API Architecture

**Internal API (Frontend):**
- Same endpoints as public API
- Authenticated via Clerk JWT
- No rate limits (internal use)
- Full CRUD access (based on user permissions)

**Public API (External):**
- Read-only (GET endpoints only)
- Authenticated via API key (Pro/Company tier)
- Rate limited
- Public data only (no private props, no email metadata)

### The API Endpoints (Public)

```
GET /api/v1/users/{username}
  → Public profile data (props, content, lineage)

GET /api/v1/users/{username}/props
  → List of public props

GET /api/v1/products/{slug}
  → Product info + advocate count

GET /api/v1/products/{slug}/advocates
  → List of public advocates (ranked)

GET /api/v1/products/{slug}/stats
  → Aggregate stats (advocate count, growth, etc.)

GET /api/v1/search/users?q={query}
  → User search (public profiles only)

GET /api/v1/search/products?q={query}
  → Product search

GET /api/v1/trending/products
  → Trending products (most added in last 30 days)
```

### The API Endpoints (Internal Only)

```
POST /api/v1/props
PATCH /api/v1/props/{id}
DELETE /api/v1/props/{id}

POST /api/v1/lineage
PATCH /api/v1/lineage/{id}

POST /api/v1/ingest/email
POST /api/v1/ingest/approve

POST /api/v1/products
PATCH /api/v1/products/{id}

POST /api/v1/content
DELETE /api/v1/content/{id}
```

### The Rate Limits

| Tier | Requests/Minute | Requests/Hour | Requests/Day |
|------|----------------|---------------|--------------|
| **Free** | 10 | 100 | 500 |
| **Pro** | 60 | 1,000 | 5,000 |
| **Company** | 120 | 2,000 | 10,000 |
| **Enterprise** | 600 | 10,000 | 50,000 |

**Burst limit:** 2x the per-minute limit for 10 seconds.

**What counts as a request:**
- Any API call (GET, POST, etc.)
- Embed widget loads (counted as API calls)
- Batch requests count as 1 request per item

### The API Key Management

```
┌─────────────────────────────────────┐
│ API Keys                                │
│                                     │
│ Active Keys:                            │
│ • prod_abc123 (created Jan 2026)      │
│   Last used: 2 hours ago              │
│   [Regenerate] [Revoke]               │
│                                     │
│ [+ Generate New Key]                  │
│                                     │
│ Usage This Month:                       │
│ 4,230 / 5,000 requests (84%)          │
│                                     │
│ [View Usage →]                        │
└─────────────────────────────────────┘
```

**Rules:**
- Max 3 active keys per account
- Keys are prefixed by environment (`prod_`, `dev_`, `test_`)
- Keys are hashed in database (only shown once at creation)
- Revoked keys are invalidated immediately

## Consequences

### Positive
- Clear separation between internal and public API
- Rate limits prevent abuse
- API keys are manageable and secure
- Webhooks enable real-time integrations
- Good documentation attracts developers

### Negative
- Public API exposes data (privacy risk)
- Rate limits may frustrate power users
- API maintenance is ongoing cost
- Webhooks require infrastructure (queue, retry logic)
- Versioning is complex (v1, v2, deprecation)

## Mitigations
- Public API only returns data that is already public on the website
- Rate limits are generous for legitimate use
- API versioning in URL path (`/api/v1/`, `/api/v2/`)
- Webhooks are Phase 4+ (not required for launch)
