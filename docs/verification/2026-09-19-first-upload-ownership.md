## Reproduction

unretained storage ID. Before the fix the promise resolved to a new raw-evidence
ID instead of rejecting. Eight existing upload tests passed while this ninth
test failed. Therefore this is a current first-claim authorization defect, not
merely uncertainty about early historical records.

## Enforced boundary

1. `beginUpload` verifies the current authenticated owner, validates filename,
   size/type and selected product, and creates a ten-minute upload ticket bound
   to both the application user and the issuer-qualified token identifier.
2. The browser sends bytes with its Convex JWT to the Convex HTTP action. A ticket
   or storage ID alone is not authorization; no cookies are used. The action
   rechecks the same owner, bounds streamed bytes, computes SHA-256 and stores
   the blob itself. It never accepts a client-selected storage ID to bind.
3. An internal-only mutation atomically binds that newly stored ID to the ticket.
   A losing identical retry returns the first ID and its extra blob is deleted.
   Different bytes cannot rebind the ticket.
4. First retention requires that exact binding and matching metadata. It saves
   `uploadAttribution` with verified-session basis, owner, issuer-qualified
   identity, ticket, receipt time and byte digest. Replay returns the same
   original without creating additional proofs. Deleted evidence cannot be
   resurrected with its ticket. The old unbound upload-URL issuer fails closed
   with a reload instruction.

This proves which authenticated owner session submitted bytes. It does not prove
who authored the file, whether its contents are authentic, whether a human or
agent performed the upload, or whether a product was used. Activity actor and
collector remain UNKNOWN; no observations, relationship confirmations, go-to
choices or publication are generated by this fix.

## Historical attribution

Existing `rawEvidence.userId`, evidence-source ownership, storage references,
metadata, capture timestamps and any existing provenance remain untouched.
Those fields record the earlier retention/account association, not verified
original uploader identity. Legacy file records without `uploadAttribution`
project an explicit **UNVERIFIED_LEGACY** status in private queries and supporting
details. New records project **VERIFIED_OWNER_SESSION**. No metadata is silently
backfilled, inferred from file dates, or promoted from the old owner field.

No production row-level attribution audit or migration occurred. The regression
fixture proves that querying a legacy record leaves its stored bytes unchanged.
Unretained legacy storage cannot be claimed by a new owner through the old API;
it must be uploaded again through the authenticated path. Previously retained
owner-scoped records remain available without inventing historical attribution.

## File-size and release compatibility

Convex's [HTTP upload documentation](https://docs.convex.dev/file-storage/upload-files)
limits HTTP requests to 20 MB. The authenticated route enforces **19 MiB** in
client validation, server ticket creation and streamed body handling. The old
25 MiB form claim is corrected. Format support is unchanged. Larger-file chunking
is not introduced by this fix. Existing retained files are not deleted or resized.

`CONVEX_SITE_URL` is Convex's built-in HTTP origin; no new secret or external
service is required. The browser supports native Convex-audience Clerk sessions
and the existing legacy template mode. Backend/schema/HTTP action must be deployed
before the corresponding frontend in any later authorized release. Old clients
must reload. This code is **not deployed or development-synchronized** here.

The added schema/table and index are additive. A process crash between blob
creation and binding can leave an unclaimed private storage object; it cannot
be adopted through first retention. Automatic abandoned-upload cleanup is not
claimed. A bound-but-unretained ticket expires; the owner must re-upload. Ticket
and attribution history are not silently removed.
